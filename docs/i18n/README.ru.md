## О проекте

PWDnow - это менеджер паролей, построенный на простом принципе: ни сервер, ни браузер, ни сеть между ними никогда не должны видеть секрет в открытом виде. Все криптографические операции выполняются внутри отдельного демона на Rust, установленного на той же машине, где хранится хранилище. Веб-интерфейс, открытый локально или предоставленный браузеру, обменивается с этим демоном только непрозрачными зашифрованными блоками данных. По умолчанию нет облачной синхронизации, нет телеметрии, и нет поставщика, которого можно было бы принудить выдать ваши данные, просто потому что он никогда ими не владеет.

Проект разделён на два уровня, взаимодействующих через локальный канал IPC:

- **Демон хранилища** (`daemon/`), написан на Rust: деривация ключей, шифрование, расшифровка, хранение через SQLCipher, блокировка памяти и безопасное стирание. Это единственная часть системы, которая когда-либо работает с ключом или учётными данными в открытом виде.
- **Веб-интерфейс** (`web/`), одностраничное приложение на React 19, обслуживаемое процессом Express: отрисовывает интерфейс, пересылает зашифрованные запросы демону через Unix-сокет и никогда не хранит ключевой материал вне короткоживущего токена сессии, находящегося только в памяти.

PWDnow может работать полностью автономно на одной машине или быть развёрнут за Nginx с TLS для доступа по локальной сети или на самостоятельно размещённом сервере. В любом случае граница доверия остаётся одной и той же: ваш мастер-пароль и ваши данные никогда не покидают защищённую память демона.

## Возможности

**Основное хранилище**
- Организация учётных данных по папкам с изменением порядка перетаскиванием
- Хранение для каждой записи пароля, секрета TOTP, заметок и пользовательских полей
- Оценка надёжности паролей, обнаружение повторного использования и обнаружение распространённых паролей
- Автономная проверка утечек с помощью локального фильтра Cuckoo, построенного на базе скомпрометированных паролей Have I Been Pwned, без сетевого запроса при каждой проверке
- Представление владельцев активов: сводный список каждого адреса электронной почты, номера телефона и аппаратного ключа безопасности, зарегистрированных среди ваших учётных данных

**Аутентификация и MFA**
- Поддержка WebAuthn и FIDO2 для аппаратных ключей безопасности и платформенных аутентификаторов (Touch ID, Windows Hello)
- Генерация TOTP (RFC 6238) и HOTP (RFC 4226) с защитой от повторного воспроизведения
- Вход без пароля с помощью синхронизированных или привязанных к устройству ключей доступа
- Настраиваемое применение MFA для каждой учётной записи

**Режимы безопасности**
- Режим принуждения: разблокировка с помощью заранее заданного альтернативного пароля запускает криминалистическую очистку вместо предоставления доступа
- Режим путешествия: скрывает выбранное подмножество учётных данных за отдельным паролем перед пересечением границы или передачей устройства
- Блокировка с экспоненциальной задержкой после повторных неудачных попыток разблокировки
- Экстренный доступ: предоставьте доверенному контакту отложенный по времени доступ к вашему хранилищу на случай, если вы станете недоступны

**Импорт и экспорт**
- Собственный формат `.p2w`: экспорт с двойным AEAD-шифрованием, дополнением и обфускацией метаданных, разработанный для устойчивости к офлайн-подделке и анализу трафика
- Экспорт и импорт в обычном JSON, CSV и XML, совместимом с KeePass
- Импорт из экспортов Bitwarden, 1Password (CSV, 1PUX) и NordPass

**Постквантовая и нормативная криптография**
- Гибридная инкапсуляция ключа X25519 + ML-KEM-768/1024 (включена по умолчанию, а не отдельная опция)
- Постквантовые подписи ML-DSA-87
- Деривация ключа Argon2id, аутентифицированное шифрование AES-256-GCM и XChaCha20-Poly1305
- Опциональный строгий режим CNSA 2.0, ограничивающий демон набором алгоритмов коммерческой национальной безопасности АНБ (HKDF-SHA-384, PBKDF2-SHA-512, а также удаление BLAKE3, SHA3, XChaCha20, Ed25519 и X25519 из активных путей кода)

## Архитектура

```
┌─────────────────────────────┐        Unix-сокет         ┌──────────────────────────────┐
│  Веб-интерфейс (web/)       │  msgpack через /run/...   │  Демон хранилища             │
│  React 19 + Express         │ ─────────────────────────▶│  (daemon/)                   │
│  Интерфейс с нулевым         │◀─────────────────────────  │  Rust, SQLCipher, mlock()   │
│  разглашением, только токен  │      зашифрованные        │  Argon2id, AES-256-GCM,     │
│  сессии, без ключей          │      ответы                │  XChaCha20-Poly1305,        │
└─────────────────────────────┘                            │  гибридный постквантовый KEM │
                                                             └──────────────────────────────┘
```

Демон предоставляет строго типизированный протокол запросов и ответов (`daemon/src/ipc/protocol.rs`), передаваемый в виде фреймов MessagePack через Unix-сокет. Каждый аутентифицированный запрос несёт токен сессии, который демон проверяет перед обращением к базе данных. Демон также проверяет личность подключающегося процесса на уровне операционной системы (`SO_PEERCRED`), поэтому дойти до него может только доверенный веб-прокси, работающий под правильным системным пользователем.

Веб-уровень никогда не получает мастер-ключ, ключ шифрования ключа, мастер-ключ хранилища или ключ шифрования данных ни в какой форме. Он получает зашифрованный текст и пересылает его. Сопутствующий демон мониторинга (`monitor/`) отслеживает рост памяти, использование диска и состояние процессов независимо от самого демона хранилища, поэтому утечка памяти или зависший процесс будут обнаружены и о них сообщат, а не приведут к незаметной деградации сервиса.

Полное техническое описание, включая иерархию деривации ключей, спецификацию формата файлов P2W и модель угроз, документировано в [`architecture.md`](../../architecture.md).

## Модель безопасности

PWDnow исходит из того, что сеть, процесс браузера и операционная система хоста потенциально враждебны, и строит архитектуру исходя из этого предположения, а не из более благоприятного.

- **Нулевое разглашение по конструкции**: браузер не может раскрыть то, чего у него никогда не было. Мастер-ключи и производные ключи существуют только в адресном пространстве демона.
- **Защита памяти**: мастер-ключ хранилища удерживается в заблокированной области памяти (`mlock`), запечатанной с помощью `mprotect(PROT_NONE)` в состоянии простоя, и стирается с помощью крейта `zeroize`, как только он больше не нужен.
- **Шифрование данных в покое**: база данных хранилища зашифрована сквозным образом с помощью SQLCipher. Экспорты используют двойное AEAD-шифрование (внутренний слой AES-256-GCM и внешний слой XChaCha20-Poly1305), с заголовком, привязанным к обеим меткам аутентификации.
- **Независимая проверка**: проект непрерывно выполняет мутационное тестирование и тестирование хаосом в своей непрерывной интеграции, в дополнение к обычным наборам модульных и сквозных тестов, специально для выявления тестов, которые проходят, фактически не проверяя заявленное поведение.

Если вы нашли уязвимость, ознакомьтесь с [Политикой безопасности](#politika-bezopasnosti), прежде чем открывать публичный тикет.

## Поддерживаемые платформы

PWDnow разрабатывается и тестируется в первую очередь на **Ubuntu 26.04 LTS (Resolute)**. Установщик также обнаруживает и поддерживает:

- Debian и производные от Debian дистрибутивы (Ubuntu, Linux Mint, Pop!_OS, Zorin, Kali)
- Fedora и дистрибутивы семейства RHEL (Fedora, RHEL, CentOS, Rocky Linux, AlmaLinux)

Инструментарий Rust поддерживает как `x86_64`, так и `aarch64`. Другие дистрибутивы Linux могут работать, но не входят в регулярную матрицу тестирования. В настоящее время сборки для macOS или Windows не существует.

## Начало работы

### Быстрая установка

```bash
git clone https://github.com/PWDnow/PWDnow-password-manager.git
cd PWDnow
./install.sh
```

Установщик определяет ваш дистрибутив, проверяет отсутствующие зависимости и предлагает их установить, проверяет конфигурацию SSH, проверяет конфликты портов, собирает демон и веб-фронтенд из исходного кода и устанавливает оба как службы systemd, работающие под выделенными непривилегированными системными пользователями. Ничего не устанавливается с повышенными привилегиями сверх того, что требуется systemd, AppArmor и установке пакетов, и каждый привилегированный шаг отображается перед выполнением.

### Сборка из исходного кода

Требования: Node.js 24 или новее, Rust 1.94 или новее (зафиксировано в `daemon/rust-toolchain.toml`), `protoc`, а также заголовки для разработки `libsodium`, `sqlcipher` и `libfido2`.

```bash
# Демон
cd daemon
cargo build --release
cargo test

# Веб
cd web
npm install
npm run build
npm start
```

Либо из каталога `deploy/`:

```bash
make build          # демон + веб, режим release
make test            # cargo test + vitest
make install          # устанавливает бинарник, юниты systemd, профиль AppArmor и конфигурацию nginx (требуется sudo)
```

Постквантовая инкапсуляция ключа включена по умолчанию. `make build-pq` и `cargo build --release --features pq-hybrid-1024` сохранены как явные псевдонимы этой же сборки по умолчанию, для ясности и совместимости со старой документацией. Используйте `--features cnsa-strict` для строгого режима CNSA 2.0.

### Настройка

Скопируйте `web/.env.example` в `web/.env` и настройте по необходимости:

| Переменная | Назначение |
|---|---|
| `DAEMON_GRPC_ADDR` | Адрес, который веб-уровень использует для связи с демоном (по умолчанию `127.0.0.1:50051`) |
| `VAULT_ORIGIN` | Разрешённое происхождение браузера в production, используется для проверки origin WebSocket |
| `BIND_HOST` | Интерфейс, на котором слушает веб-сервер (по умолчанию `127.0.0.1`; установите `0.0.0.0` для доступа по локальной сети) |
| `SSL`, `SSL_PORT`, `SSL_DIR` | Опциональный самоподписанный HTTPS, генерируется скриптом `web/scripts/generate-ssl.sh` |

## Использование

При первом запуске `Setup.tsx` проводит через создание хранилища: выбор мастер-пароля, опциональная регистрация аппаратного ключа безопасности или TOTP, после чего демон создаёт зашифрованную базу данных SQLCipher, а также сопроводительный файл в открытом виде, в котором фиксируется только то, что нужно странице входа (какие методы MFA настроены, включён ли вообще вход по паролю), чтобы ничего не приходилось расшифровывать до вашей аутентификации.

Далее вы можете:

- Организовывать учётные данные по папкам, добавлять пользовательские поля и генерировать надёжные пароли прямо на месте
- Включить режим принуждения и режим путешествия в настройках, если хотите иметь возможность продемонстрировать правдоподобное безопасное состояние под принуждением или при пересечении границы
- Запустить встроенный монитор утечек, чтобы проверить сохранённые пароли по локальной автономной копии известных скомпрометированных паролей, без исходящего запроса на каждый пароль
- Экспортировать файл `.p2w` для резервного копирования или импортировать из другого менеджера паролей, никогда не покидая своей машины

## Разработка

Структура репозитория:

```
PWDnow/
├── daemon/     Демон хранилища на Rust. Вся криптография находится здесь.
├── web/        Фронтенд на React 19 + Express и IPC-прокси.
├── monitor/    Независимый процесс на Rust для мониторинга и обнаружения утечек памяти.
├── deploy/     Юниты systemd, профиль AppArmor, конфигурация Nginx, Makefile.
├── proto/      Определения gRPC/protobuf, общие для демона и веб-части.
└── hibp/       Скрипт, который собирает автономный фильтр Cuckoo HIBP.
```


## Тестирование

```bash
# Демон
cd daemon && cargo test
cargo test -- <test_name>       # запустить один тест

# Модульные тесты веб-части
cd web && npm run test
npx vitest run src/utils/crypto.test.ts   # один файл

# Сквозные тесты (Playwright)
cd web && npx playwright test
npx playwright test e2e/comprehensive-platform.spec.ts   # полный регрессионный прогон
```

Непрерывная интеграция запускает модульные тесты, сквозные тесты, аудит зависимостей, мутационное тестирование и тестирование хаосом при каждом push и pull request. `web/e2e/comprehensive-platform.spec.ts` служит регрессионным шлюзом: он проходит через аутентификацию (успешные и неуспешные пути), навигацию, CRUD-операции с папками и учётными данными, режим принуждения и уничтожение учётной записи, и должен проходить перед выпуском любого изменения фронтенда или аутентификации.

## Развёртывание

Для любого использования за пределами одной локальной машины поставьте Nginx перед процессом Express:

- `deploy/nginx/vault.conf` обрабатывает завершение TLS, HSTS и ограничение частоты запросов. Nginx не должен устанавливать собственный заголовок Content-Security-Policy, поскольку сервер Express добавляет новый nonce при каждом запросе.
- `deploy/vault-daemon.service` запускает демон под выделенным системным пользователем `vault`, с `MemorySwapMax=0`, `NoNewPrivileges`, `PrivateTmp` и только той возможностью `CAP_IPC_LOCK`, которая нужна для блокировки памяти.
- `deploy/apparmor.d/vault-daemon` ограничивает доступ демона к файловой системе и возможностям на уровне ядра и применяется без изменений как на хостах `x86_64`, так и на `aarch64`.

`make install` (или `install.sh` для полной управляемой установки) связывает всё это воедино, включая загрузку профиля AppArmor и включение юнитов systemd.

## Политика безопасности

PWDnow работает с учётными данными, поэтому отчёт об уязвимости здесь важнее, чем в большинстве проектов. Если вы обнаружили проблему безопасности, пожалуйста, не открывайте публичный тикет. Вместо этого воспользуйтесь функцией приватного сообщения об уязвимостях GitHub для этого репозитория или свяжитесь напрямую с сопровождающими. Приложите достаточно подробностей для воспроизведения проблемы и, по возможности, оценку воздействия. Мы оперативно подтвердим получение отчёта и укажем автора, если он этого пожелает, после выпуска исправления.

## Участие в проекте

Тикеты и pull request приветствуются. Прежде чем отправить изменение:

- Запустите `make lint` (`cargo clippy -D warnings` и `tsc --noEmit`) и `make test`
- Для изменений фронтенда или аутентификации запустите полный регрессионный набор Playwright
- Оставляйте криптографические изменения только в демоне; веб-уровень никогда не должен получать доступ к ключевому материалу как побочный эффект изменения функциональности
